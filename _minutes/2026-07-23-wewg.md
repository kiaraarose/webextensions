Making Progress on Spec Document

 * [timothy] What do we need to do to make more progress on the spec? We've had a number of proposals mired in review.
 * [timothy] Floating an idea, shorter approval windows (1 week/5 days) and follow up with additional PRs to refine as necessary.
 * [devlin] Generally think that's in line with what we want. Trepidation around landing with errors. Think it's okay if we land incomplete. Take `web_accessible_resources` (WAR). There are a lot of things to cover. We can start small (“WAR allows extensions to expose contents to websites”), land that and go from there. There is some impression that what's landed is agreed upon by the group. Should do our due diligence to make sure what we land is accurate. I'd rather have omissions and small rapid steps than a 5 page PR with errors that we can fix later.
 * [rob] Specify extension context PR (905) was originally a 5 line short statement. As I was working on that, I expanded to include isolated worlds, which ended up being a discussion topic. In cases like this, should we split out isolated worlds and land that separately?
 * [timothy] Yeah, that's the quagmire I was referring to. We should split.
 * [devlin] When reviewing a PR, we should ask for corrections and be less focused on asking for additions.
 * [timothy] Or add notes. Isn't there a way to call out something needs work?
 * [simeon] Yeah, there's a way to flag an issue in the document and link to additional discussion.
 * [tomislav] LIke your framing of having reviews ask for corrects, new content should be in a follow up. Can try to maintain a 1 week turnaround for most things.
 * [oliver] Similarly, if someone adds a comment to your PR that you feel adds too much, you're empowered to say no and ask to break out into a follow-up.
 * [oliver] Currently APIs are not specified. E.g. recent changes to alarms API could have been specified, but it feels like there is a high bar to specifying it. Is it worth coming up with an idea of what it looks like to spec out an API.
 * [timothy] Should have more of the shell filled out.
 * [simeon] Now that I've created PR 1049, I was thinking about working on building out this shell. I'll commit an action item to building that out before our next meeting.
 * [carlos] It would help to distinguish specing out existing APIs from accepted proposals from the community group. The latter would be a great use of our time considering the pending implementation and would greatly help outline the specifics on our process as it is way more contained of a process compared to specing out existing APIs. An example is the browser.runtime.onExtensionLoaded.
 * [timothy] Good signal for what to work on next.
 * [carlos] Better use of our time to  document new things than just existing ones.
 * [timothy] Existing APIs are broadly compatible. There are a lot of details that need work, but the high level shape is there.
 * [oliver] Happy working with Simeon to add an API. We can figure out what that is and where it lives in the content structure.
 * [rob] `alarms` might be a good starting point, since it is fresh in your mind. There are nuances, but could be useful to start small and iterate.
 * [oliver] I think we're mostly aligned on that one.
 * [timothy] There are some details. Know we've discussed before how times align, etc. Start high level and add details.
 * [devlin] Don't think that case is bikeshedding. It's that we probably all do different things and no one knows what the right thing to do is.
 * [timothy] At the same time, don't want to do what the HTML spec did a long time ago, documenting aspiration rather than what we all implement.
 * [devlin] Should spec what we actually do.
 * [oliver] I think we've all implemented what we've agreed on.
 * [rob] Do we want to start that or maybe something with promises and callbacks? Saw some recent feedback about inconsistencies here and the poor developer experience.
 * [devlin] In a perfect word we'd specify typical behavior and go into each individual API. In general I don't think we'd specify that you must do one or the other. Invalid signature will throw immediately, something that has to be parsed in another process has to be asynchronous
 * [rob] From a browser engineering perspective that's natural, but…
 * [devlin] Also common in web APIs. Less common on the web for historical reasons, but increasingly common in new, powerful APIs. I'd probably push back on anything that tries to be dogmatic about what to do where.
 * [timothy] What would your ideal be, Rob?
 * [rob] Write down something like if a property is unrecognized we throw an error immediately.
 * [timothy] Open to changing. Recognize as a useful feature detection capability. We already throw for invalid types for recognized properties. But yes, useful to write down that sometimes we throw and sometimes we reject, in the spec.

WPT Tests

 * [kiara] We have new additions, added by Justin from Google. Previously we stated that tests should accompany a spec. Is that still a goal? That tests and spec accompany each other?
 * [devlin] I think we want both. ATM I don't think it's in our best interest to block on both. Don't think we should deny a WPT test because someone didn't write a test and vice versa.
 * [kiara] Also wanted to discuss the process of reviewing new tests and new harness changes going forward. E.g. recently Google landed changes that broke all tests in Firefox due to their lack of support for service workers in extensions. What is our process for adding new tests, reviewing, aligning on behavior of the tests, what we expect to pass?
 * [devlin] Two parts there: review process and what we want to land. Probably don't want to land browser-specific features that are not implemented elsewhere in WPT. In terms of review, WPT process is established. Hesitant to change that or impose new requirements. In cases like this, suggest we open a PR to remove the change and discuss impact out of band.
 * [oliver] We have had a brief discussion about this; wpt guidance is that one review from a member of the repo is sufficient. In principle I agree that if we were to set up our own repo that the review process like the WECG would make sense to wait for review. But the toolings etc are not prepared with that workflow, e.g. wpt has automation to create PRs for tests landed in browser-specific repos, to upstream to wpt. Suggest embracing the wpt workflow.
 * [simeon] I'm not familiar; what happens if we revert a change after it lands in wpt?
 * [devlin] Removal gets auto-merged into each browser.
 * [simeon] So if something bad lands in WPT, how do we correct and minimize breakage?
 * [devlin] Short version, we land a revert in the browser, PR is automatically submitted to wpt.
 * [tomislav] I think other groups work like that. There's at least some sanity check / due diligence that something is supported in another browser.
 * [kiara] should we be testing changes in other browsers when making harness changes?
 * [devlin] For silly reasons that will be difficult on the Google side. We're locked down on what software we can run. May be difficult to test in the nightly versions of other browsers.
 * [rob] Do we have the ability to open up CI infrastructure to get test results back?
 * [devlin] You'd have to be able to pull down the source for the other browser have a commit to that project. Unless you mean CI infrastructure in WPT.
 * [oliver] I opened a PR on WPT repo and checked the “checks” tab with the CI runs. On first glance it seems like it tries to run SafariDriver and run tests. Sounds like if we did open a PR it should have run the tests?
 * [timothy] That sounds right.
 * [oliver] Not clear landing in Chromium creates a PR in WPT.
 * [rob] Could be a good action item to check what's available and whether WPT is open to creating PRs just to kick of CI jobs.
 * [timothy] Maybe a draft PR? Signal you want the test to run but you're not (yet) looking for a review.
 * [tomislav] I'll look into it.
 * [simeon] Could potentially integrate some of this content into 1049. Then again, maybe that will bloat that one resource too much.
