[Issue 1039](https://github.com/w3c/webextensions/issues/1039): Proposal: cross-browser support for cross-origin isolation on extension pages (COOP/COEP manifest keys)

 * [oliver] If I understand the request correctly, this is requesting a feature already implemented in Chrome.
 * [rob] Firefox doesn't isolate different extensions; they run in the same process. We recently implemented the “sandbox” manifest key, in theory we could consider COOP/COEP for these.
 * [timothy] Wasn't aware of these keys. We'll need to figure something out for WebKit. We haven't had a request for this.
 * [rob] What do you think of the sandbox idea? Does Safari run extensions as separate processes?
 * [timothy] Yes, each extension gets its own web process. There is a difference when it comes to frames - if a frame embeds an extension page. That's more like content scripts, at least until we have full isolation, which we're working on.
 * [rob] What happens in Chrome when you have web accessible iframes when an extension declares COOP/COEP?
 * [oliver] Not sure.
 * [rob] I would expect it to not be isolated, but I have not checked. I think we'd all be supportive, correct? So supportive Firefox and Safari, implemented Chrome.
 * [timothy] I think so, yes.
 * [rob] COOP/COEP enables use of APIs that can potentially leak information to other content in the same process, which is why Firefox does not offer the capability unless it puts each extension in their own process. A potential way to support the functionality is to add COOP/COEP support to sandboxed extension pages, since there is nothing sensitive to leak there. Would you be open to that in other browsers?
 * [rob] Just landed a patch for sandboxed pages. Will ship in 154.
 * [timothy] Safari does not support the sandbox feature yet.

[Issue 1042](https://github.com/w3c/webextensions/issues/1042): Add ability to determine if a tab is a new tab page

 * [carlos] Extensions may want to know if a given tab is a new tab page for multiple reasons: determining if it can be easily overwritten, whether the tab should be tracked in history, etc. I proposed exposing a new boolean property in the Tab object to signal this.
 * [timothy] Might also be another extension.
 * [carlos] Some browsers may lie about new tab pages. Aim is to remove this complexity moving forward.
 * [rob] Example use cases?
 * [carlos] I have an extension that allows you to open sites like a bookmark manager. If you trigger a link on a new tab, you may want to navigate that tab.
 * [rob] Hesitation here is that it could be difficult to tell if something is a new tab. For your use case, you can accept anything that looks like a new tab. You may want to differentiate between a new tab page, split view temp page, etc. Exposing a new property on tabs.Tab would ideally have general utility. Don't see a problem with exposing a method that takes options.
 * [carlos] Simeon had an idea about normalizing new tab urls.
 * [simeon] Basically, if we had a single well known URL that was exposed to extension for a new tab, extensions could check against that well known URL. Could also expose the well known URL as a global property on an appropriate namesapce.
 * [timothy] At that point it may as well be a bool. I'm in favor of a new property on the tab object.
 * [brandon] Would we want to add something to tabs.query as well?
 * [simeon] I would, yes.
 * [carlos] That would be a benefit of a property.
 * [oliver] Ways to tie this to a documentId? Actually, not sure if we expose a documentId on tabs.
 * [timothy] We wouldn't have a documentId for a new tab page.
 * [rob] Clarification, why a property rather than a method?
 * [timothy] The object is a snapshot. Doesn't need to be as complicated as a new method.
 * [rob] Right, it's a frequently taken snapshot across many APIs. I'd prefer to make this separate as a conditionally available property exposed behind, say, a permission.
 * [timothy] Doesn't seem expensive to calculate.
 * [rob] There are more expensive things, of course. Not a deal breaker. Complexities here around whether home pages would be considered a new tab.
 * [timothy] We wouldn't consider it a new tab. I think the definition would be the browser's built-in start page or an extension that's configured as a new tab page. If the browser is configured to a blank new tab or [yahoo.com](http://yahoo.com/) or whatever, that wouldn't count.
 * [rob] Would that implementation be useful to you, Carlos?
 * [carlos] Yes.
 * [rob] Another developer expressed interest. Brandon, thoughts on what this flag should reflect? Home pages, blank pages, etc.
 * [brandon] For our use case we considered all of those new tab pages.
 * [carlos] My use case also covered about:home and about:blank.
 * [rob] Sounds like there's interest in further discussing, but we would need a more concrete idea of what this would cover, as there seems to be a non-exact overlap of what is expected and what browser vendors consider to be in-scope. Doesn't have to be a full proposal, but something to facilitate discussion and alignment.
 * [carlos] Sounds good.
 * [oliver] We don't support setting an arbitrary url for a new tab page.
 * [simeon] No, but it does support opening a new tab to your home page, and that is settable to arbitrary URLs.
 * [oliver] Gut feeling is that this would be distinct.
 * [carlos] Just tested; Home page can be set to the NTP, but when you open a new tab, that tab is fixed.
 * [rob] There are some extensions overriding the newtab page, and redirecting elsewhere based on user customization. Would be nice (not required) to include some thoughts on that scenario.
 * [carlos] Brandon, can you also share more use cases from 1Password on the issue?
 * [brandon] +1
 * Next steps: Carlos is going to draft a proposal on how to approach this.

[Issue 999](https://github.com/w3c/webextensions/issues/999): Proposal: "name" attribute in second argument of alarms.create()

 * [simeon] Looking to get browser stances on `alarms.create({name})`, which would move "name" from an argument to a property.
 * [oliver] Supportive on Chrome's side.  Right now if you want to create an alarm with an name, you need to specify it as the first parameter. This would allow you to declare a name as a property on the options object. Just a bit more ergonomic to use.
 * [rob] Anything on the validation constraints here? If you declare it in the first parameter and in a property, what happens?
 * [oliver] The Chromium patch Anton is working on original picked one, but was recently updated to throw if both are provided.
 * [carlos] If they're the same, maybe that's acceptable?
 * [simeon] Feels like a footgun waiting to happen.
 * [timothy] Some backwards compatibility concerns that this will just fail in older browsers.
 * [carlos] Could be a reason to include both and tolerating it.
 * [oliver] Doesn't see how that helps. If the only value you get is being able to specify the name in a more ergonomic way, having to specify both seems worse.
 * [rob] I see an argument in favor of being more strict. I think Safari is more accepting of unknown properties (in contrast to Firefox and Chrome). If validation is stricter, extensions can try to feature-detect availability in Safari.
 * [timothy] Name is currently a required argument. If you fail to pass a string, Safari would throw. We also wouldn't throw if name is in the object and we don't recognize it.
 * [rob] Name is optional.
 * [timothy] My mistake. By throwing for unknown keys, Firefox and Chrome will start throwing if developers include this property in older browsers.
 * [rob] That's why it would be opt-in.
 * [simeon] As in a new permission?
 * [rob] No, when developers adopt this pattern, they would need to know it's not backwards compatible.
 * [timothy] As long as both are documented.
 * [oliver] Not sure if there's precedent, but would we be aligned on describing the name property as deprecated once this is implemented across browsers?
 * [simeon] I'd be in favor.
 * [rob] I'd be open to that, despite it not carrying any status. At the least we can recommend the new usage. As long as supported browser versions do not support the old method, extension developers cannot really get rid of it though.
