[Issue 1028](https://github.com/w3c/webextensions/issues/1028): Proposal: Limits on how much data can be set or retrieved at once for extensions with unlimited storage

 * [kiara] I opened this. Addresses an issue we've observed in Safari.
 * [oliver] Initial reaction was the same as [Rob's comment in the issue](https://github.com/w3c/webextensions/issues/1028#issuecomment-4745551297): whether we should define specific limit or just define how we handle these situations.
 * [timothy] Also a platform-dependent concern. Specifically observed on iOS.
 * [rob] What is the limit you've chosen?
 * [kiara] One gigabyte, uniform between iOS and macOS.
 * [rob] What happens when the limit is reached?
 * [kiara] Some descriptive error.
 * [tomislav] I think we have a hard IPC layer limitation of ~256 MB.
 * [rob] Special case and implementation detail of Firefox, not affected by the usual extension API's IPC limits. Comes back to what we think is a reasonable limit enforceable everywhere. I'm concerned about backwards compatibility. If that's not a concern, 1GB could be reasonable.
 * [oliver] Anecdotally people push more data than you'd expect through these APIs. On our side we'd want to add metrics and gather data before adding a hard limit. We also have IPC limits that come into play, but don't know what they are off the top of my head.
 * [rob] Have we also discussed limits on `tabs.sendMessage`? It is IPC and unlike `storage.local` there is no persistence component to it.
 * [oliver] Don't specifically recall. More generally, should we have a limit per API or a general limit?
 * [kiara] Could take the approach of bucketing by category where similar categories have similar limits.
 * [rob] Would be nice to have some consistent behavior across browsers, intentionally throw or crash. On the other hand, the default web behavior is to eventually crash or throw. Would be nice to address, but not sure concretely what would be the right approach.
 * [carlos] Should we expose the limit to developers so they can adapt?
 * [rob] If there's a fixed limit, worth considering. If not, could signal free space on disk, which would leak information not currently exposed.
 * [oliver] Worry that 1Gb limit could be a global limit, but due to system pressure you can only send 500 Mb. A hard limit should stop an outright crash in most scenarios.
 * [kiara] Oliver, I'd love to hear more if you gather stats in Chrome.

[Issue 1032](https://github.com/w3c/webextensions/issues/1032): How should we empower extensions to add new permissions without overly alarming their current user base?

 * Comparing:
   * [PR 798](https://github.com/w3c/webextensions/pull/798): Proposal "Allow to change permissions behavior on extension updates"
   * [PR 883](https://github.com/w3c/webextensions/pull/883): Proposal: `initial_permissions` and `initial_host_permissions`
 * [benjamin] In the last meeting we discussed the key differences between the two proposals (links TBD). Carlos called out that 883 solves several related issues. Rough idea here was that developers don't have a good option for adding a new permission that would cause a warning and interrupt the upgrade process or cause them to be disabled. I produced a summary specifically focusing on that context. There's a lot here, so may not be valuable to read through everything now. 3 major thematics I saw were scope: 798 is narrow, 883 addresses a larger set of concerns. Backwards compatibility: … 883 provides a means of getting around this via the old options key fallback. Discoverability: applies more to 883, as it adds complexity to permissions overlap. Also questions of revokability. That's very high level.
 * [berjamin] Having gone through these two, I have a new proposal ([XKCD comic here](https://xkcd.com/927/)). In my proposal we'd have permissions and optional_permissions as we do now, and in the middle we'd have `deferrable_permissions`, which would be treated as optional on update and required on install. To ensure fallback behavior in browsers that don't support the new key, developers would declare permissions in both `deferrable_permissions` and `optional_permissions`.
 * [oliver] Hadn't seen this. Thanks for doing the work. Looking forward to reading.
 * [kiara] Thanks. Took a glance, leaning towards deferrable permissions but need to read more closely.
 * [carlos] Thanks! The complexity from 883 is directly related to it attempting to solve many issues at once. If vendors are more likely to go for `deferrable_permissions`, happy to support that.
 * [timothy] I tend to lean towards the defer proposal. Seems like the most natural progression of what we currently have.
 * [rob] Does deferrable combine permissions and host permissions?
 * [benjamin] I'd say you'd have a pair for deferrable permissions and host permissions.
 * [timothy] Please update the description to clarify what you have in mind.
 * [rob] Next step is probably to check in with Devlin on Chrome. Right now in Firefox we postpone updates. With this change we could potentially take the property as a signal to force-disable / updates, but that could go against user preference.
 * [oliver] Will aim to follow up async so we can have some discussion before the next meeting.

[Issue 1035](https://github.com/w3c/webextensions/issues/1035): Inconsistency: valid characters in extension resource URLs

 * [anton] Inconsistencies between potentially acceptable characters in extension paths, depending on file path, case-insensitive file systems, zip file format, URL logic, and web store validation.
 * [oliver] We've added some checks to CWS to make sure there are completely distinct names in a case insensitive way. If others have strong feelings, the browser could have different behavior - currently it's only enforced at the store level.
 * [kiara] I'd have to test to see if we allow packaging of the same file names with different casing. Seems like a reasonable request on the packaging side.
 * [timothy] On macOS it depends on whether your disk is configured to be case sensitive or not.
 * [oliver] Saw mention of URL encodings as well. I'm inclined to say we should align with the web as much as we can.
 * [oliver] I think that makes sense. Willing to be wrong if there's notable use case.
 * [rob] Some of the issues are dependent on the filesystem. If the FS is not case sensitive, then you get the same fallback regardless of casing. When packed in a zip file they are case sensitive. When loading via about:debugging in Firefox, there are some differences in what's allowed by the filesystem. If we load from a packed extension, we follow the rules of the zip file. This is confusing and there is a bug tracking this at:
   * https://bugzilla.mozilla.org/show_bug.cgi?id=1827656: “Warn or reject when moz-extension:-URL in temporary extension is invalid when packed as xpi”
 * [oliver] As I understand it, Firefox doesn't extract files from the zip for packed extensions, it reads them directly from the zip.
 * [rob] Correct. Chrome does the opposite: it extracts files to disk and reads the extracted files. What does Safari do?
 * [kiara] I believe we extract.
 * [timothy] Correct. So behavior depends on the host's filesystem. Read from the app package, which are just files on disk.
 * [rob] Next steps?
 * [oliver] For next steps, I can follow up with the Chrome team on how we want to approach validation.
 * [rob] I expect we wouldn't want to break existing extensions. Can you gather data or telemetry on the impact of case sensitivity on the existing set of published extensions?
 * [timothy] It will be platform dependent too because on macOS a colon is invalid in a file name for legacy reasons. That said, we should solidify on (at least) web safe and case insensitive values.
 * [rob] That's difficult. If we follow the conventions of the web, URLs are case sensitive.
 * [oliver] Potentially different between what we allow the browser to load and what's accepted in the URL bar.
 * [simeon] Note that hostnames are converted to lowercase when resolving a URL.

[Issue 1036](https://github.com/w3c/webextensions/issues/1036): The userScripts API should provide a method/option to register overwriting an existing id without us explicitly checking first whether it exists or not

 * [oliver] Initial thought is maybe we make `userScripts.register` override by default. Been thinking about this type of issue with respect to declarative net request rules. Seems like most developers want overwrite behavior in these sorts of APIs.
 * [rob] I see extensions doing that. Not limited to user scripts or DNR. Another major example I have seen is contextMenus. Could be addressed with a flag that allows changing the default behavior, and use that convention across multiple APIs (`persistAcrossSessions` is also an example of a flag that appears in more APIs, first `scripting` now also `alarms`).
 * [simeon] I think I'm also inclined towards the optional parameter, but an alternative would be to introduce an “upsert” so there's explicit behavior at the method level.
 * [rob] Partial registering and partial creation is non-trival. Not impossible by any means, just requires work that someone would have to do. I'm open to reviewing patches.

[Issue 238](https://github.com/w3c/webextensions/issues/283#issuecomment-4643322637): Spec clarification: handling of version strings with leading zeros in browser UI and stores

 * [rob] I think requests for MV4 are not likely to be implemented any time soon. Store changes are outside the group, but can always ask. A use case for leading zeros I've seen is for versions formatted as dates.
 * [carlos] Could put it in the last part of the version. For example, `X.Y.Z.20260702`.
 * [kiara] Wouldn't be opposed.
 * [simeon] +1
